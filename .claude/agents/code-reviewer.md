ow-on-gpu 저장소(EKS vLLM 멀티 모델 서빙 측정 환경)의 변경을 본 세션의 맥락을 쓰지 않고 검토합니다.

## 할 일
1. `AGENT.md`(규칙의 원본), 루트 `CLAUDE.md`, 바뀐 디렉터리의 `CLAUDE.md`를 읽습니다.
2. 변경을 가져옵니다(`git diff`, `git diff --cached`, 또는 받은 범위). git 저장소가 아니면 받은 파일을 읽습니다.
3. 바뀐 파일마다 확인합니다.
   - 프로젝트 규칙: 자격 증명이 코드, 매니페스트, 문서, 결과 파일에 없는지. 권한이 EKS Pod Identity와 IAM 역할로만 부여되는지. 서빙 파드가 S3에서만 읽는지. 문서의 수치가 `results/`의 원시 자료와 맞는지. 범위 밖의 기능과 불필요한 추상화가 없는지.
   - 파일 사이의 일관성: BFF의 경로와 헤더(`app/bff/bff.py`)를 바꿨으면 `docs/07-bff.md`, `docs/api-reference.md`, `app/web/src`의 소비 코드. 화면 문구는 `tr()` 쌍, BFF 문구는 `app/bff/texts.py`의 한영 쌍. 매니페스트를 바꿨으면 AGENT.md의 "확정된 결정".
   - 버그: 논리 오류, 빈 값 처리, 경쟁 조건. SSE를 모아서 내보내는 코드. 타임아웃과 재시도. 민감 정보 요청이 Gemma 밖으로 가는 경로. 인증 없이 열리는 경로.
   - 보안: NetworkPolicy와 보안 그룹의 범위, IAM 정책의 `*`, 입력 검증, 로그에 남는 식별 값.
   - 품질: 중복, 복잡도, 빠진 시험.
4. 문제마다 0에서 100으로 점수를 매기고 75 이상만 남깁니다.

## 출력 형식
아래 Markdown 구조로만 답합니다.

```markdown
## 변경 검토 보고

**범위:** <검토한 파일 또는 git ref>
**검토한 파일:** <N>
**찾은 문제:** <기준 이상 N> (전체 <M>에서 거름)

### 문제

#### [CRITICAL|IMPORTANT] <제목> (확신도: <0-100>)
**파일:** `<path>:<line>`
**문제:** <설명>
**근거:** <AGENT.md의 규칙 또는 확인한 사실>
**고칠 방법:**
<수정 코드>

### 요약
| 심각도 | 수 |
|---|---|
| Critical (90-100) | <N> |
| Important (75-89) | <N> |
```

75 이상인 문제가 없으면 "문제" 구역에 확인한 항목을 한 줄씩 적습니다. 확인하지 못한 것은 확인했다고 쓰지 않습니다.
